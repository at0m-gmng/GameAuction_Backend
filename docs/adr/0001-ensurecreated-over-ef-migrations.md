# ADR 0001 — EnsureCreated и идемпотентные патчи вместо EF Migrations

**Статус:** принято

## Контекст

Схема БД эволюционирует (новые колонки, индексы, внешние ключи). Боевые базы уже развёрнуты на Neon и содержат данные. Стандартный инструмент — EF Core Migrations, но:

- генерация миграций (`dotnet ef migrations add`) требует локальной сборки проекта, а на машине разработки сборка .NET падает с ошибкой CET (специфика Windows-окружения, не кода);
- проект демонстрационный, схема простая, сервисов немного.

## Решение

Использовать `context.Database.EnsureCreatedAsync()` для создания схемы на чистой БД, а изменения существующей схемы накатывать **идемпотентными raw-SQL патчами** на старте сервиса: `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, добавление FK через `DO`-блок с проверкой `pg_constraint`, разовые бэкфиллы.

## Последствия

**Плюсы:** не нужен migration-тулинг и рабочее локальное окружение; на чистой БД схема поднимается сама.

**Минусы (осознанный техдолг):**
- каждое изменение схемы — ручной идемпотентный SQL, легко забыть (в проекте это уже приводило к рассинхрону кода и боевой БД);
- нет версионной истории схемы и down-миграций;
- `EnsureCreated` и Migrations взаимоисключающи.

## Путь к миграциям

Ограничение — только локальный тулинг (CET — специфика Windows). Генерация в Linux-контейнере SDK или в CI-джобе не затронута. Переход: сгенерировать `InitialCreate` в CI/контейнере, заменить `EnsureCreatedAsync` на `MigrateAsync`, для существующих БД — baseline или пересоздание. Отложено до выхода за рамки демо.
